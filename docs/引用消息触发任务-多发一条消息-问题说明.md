# 引用消息触发任务 — 多发一条乱码消息问题说明

> 前端反馈文档 · 供后端定位与修复（2026-08-20）

## 1. 问题现象

群聊中「引用 DIFF 消息继续修改」并发送后，前端只发出一条正常消息，但消息列表里会**额外多出一条**用户自己的气泡，内容是把引用协议 JSON 序列化成的文本：

```
@编排助手 {"replyText": "readme文件的最后补一句七夕不快乐", "quotedText": "[Diff] 分析一下现在这个项目并加一个README", "quotedMessageId": "01a019c5-24a4-7ab5-a781-e7f6ed5de691", "quotedSenderName": "编排助手"}
```

这条消息 `type=TEXT`、`senderType=USER`（伪装成原发送用户）、`replyToId=null`、`mentions=[]`，显示在用户自己的气泡里，看起来像"自动多发了一条"。

## 2. 复现步骤

1. 群聊中收到一条 `type=DIFF` 的消息（Agent 交付）。
2. 点击该 DIFF 卡上的「引用继续修改」。
3. 输入正文（可含或不含 `@编排助手`），发送。
4. 观察消息列表：正常 QUOTE 消息（sequence N）之外，多出一条 `@编排助手 {…JSON…}` 的 TEXT 消息（sequence N+1）。

## 3. 关键证据（消息列表原始数据）

同一时刻的两条消息（同一用户、同一群）：

### 3.1 sequence 30 —— 正常消息（前端发出）

```json
{
  "id": "01a01dbd-4250-714a-b6fa-c9489a358fe4",
  "type": "QUOTE",
  "content": {
    "replyText": "readme文件的最后补一句七夕不快乐",
    "quotedText": "[Diff] 分析一下现在这个项目并加一个README",
    "quotedMessageId": "01a019c5-24a4-7ab5-a781-e7f6ed5de691",
    "quotedSenderName": "编排助手"
  },
  "senderId": "01a0033b-f36c-7c68-bc4e-76f437f4f050",
  "senderType": "USER",
  "replyToId": "01a019c5-24a4-7ab5-a781-e7f6ed5de691",
  "replyText": "readme文件的最后补一句七夕不快乐",
  "mentions": []
}
```

### 3.2 sequence 31 —— 异常消息（多出的那条）

```json
{
  "id": "01a01dbd-4c1f-7cb9-be69-317e93046227",
  "type": "TEXT",
  "content": {
    "text": "@编排助手 {\"replyText\": \"readme文件的最后补一句七夕不快乐\", \"quotedText\": \"[Diff] 分析一下现在这个项目并加一个README\", \"quotedMessageId\": \"01a019c5-24a4-7ab5-a781-e7f6ed5de691\", \"quotedSenderName\": \"编排助手\"}"
  },
  "senderId": "01a0033b-f36c-7c68-bc4e-76f437f4f050",
  "senderType": "USER",
  "replyToId": null,
  "replyText": null,
  "mentions": []
}
```

### 3.3 判定依据：JSON 键序

sequence 31 的 `content.text` 内嵌 JSON 的键序为：

```
replyText → quotedText → quotedMessageId → quotedSenderName
```

与 **sequence 30 的 content（后端存储/回传顺序）完全一致**。

而前端 `handleSend` 构造 QUOTE content 的键序是：

```
quotedMessageId → quotedText → quotedSenderName → replyText
```

**结论**：sequence 31 不可能是前端发出的（前端无 `JSON.stringify(content)` 拼文本的代码，键序也不符）。它是**后端**在「引用消息触发任务」处理链路中，把**存储后的 QUOTE content 序列化成文本、前缀 `@编排助手`、并以原用户身份**自动插入的一条复制消息。

## 4. 问题根因（后端侧）

后端在处理"引用（QUOTE/DIFF）消息 → 触发新任务"时，额外插入了一条消息，但：

1. `type` 存成了 `TEXT`，`content.text` 是**被引用消息 content 的 JSON 序列化字符串**（而非结构化 content）；
2. `senderId`/`senderType` 伪装成原发送用户（导致前端显示为用户自己的气泡）；
3. `replyToId`、`mentions` 为空，丢失引用关系与 @ 提及。

## 5. 后端修复建议

- **最理想**：删除这条自动插入的消息——前端已发送并正常保存了 QUOTE 消息（sequence 30），触发任务不需要再复制一条。
- 若必须插入"任务已创建/触发确认"类消息：
  - 保持 `type=QUOTE` 结构：`content` 为 `{ quotedMessageId, quotedText, quotedSenderName }`、顶层 `replyText`、`replyToId` 指向被引用消息；
  - 或使用明文 `TEXT`（如"已根据你的引用创建任务"），**不要**把 content 序列化进 `text`；
  - `senderType` 应反映真实发送方（Agent/系统），不要伪装成用户。
- 可参考现有契约：引用协议见群聊消息 `type=QUOTE` 的存储/回传结构（§7：`replyText` 顶层字段冻结）。

## 6. 前端现状（临时防御，待后端修复后移除）

前端已加临时防御（commit `b55d4c5`）：

- 识别 `type=TEXT` 且 `content.text` 形如 `@某Agent {…含 "quotedMessageId" 的 JSON…}` 的消息，整条隐藏，不再显示乱码；
- 正常用户文本不会命中该特征；
- **后端修复后，该特征自然不再出现，前端这段防御可移除**（前端会跟进清理）。

## 7. 验证方式

修复后复现步骤 2 的流程，确认消息列表中**只出现一条** QUOTE 消息（无 sequence N+1 的 TEXT 乱码）。
